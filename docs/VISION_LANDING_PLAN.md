## 参考项目读到了什么

参考：[09priyamgupta/px4_vision_landing_staticTag](https://github.com/09priyamgupta/px4_vision_landing_staticTag)。本次审阅版本为 [`e06a44357daff2b62182e3e35943e134f3be73c2`](https://github.com/09priyamgupta/px4_vision_landing_staticTag/tree/e06a44357daff2b62182e3e35943e134f3be73c2)，读取了 README、package.xml、两个 launch、frames/AprilTag 配置、任务管理器、视觉控制器和坐标工具。下列是源码静态审阅结论，不是本地复现实验结论。正式复现若采用其他提交，应重新核对差异。

| 位置 | 读到的实现或差异 | 本项目怎么处理 |
|---|---|---|
| README | 环境为 Ubuntu 22.04 / Humble / Garden；报告约 4.7 cm 落点误差 | 只作为作者报告；Jazzy/Harmonic 要重新做环境、接口和误差验收 |
| `launch/apriltag_pipeline.launch.py` | image_proc 整流，再调用 apriltag_ros；图像话题固定为 `/x500/camera/...` | 先查实际相机话题、消息类型、插件名和参数，不能只替换发行版名称 |
| `launch/landing.launch.py` | 日志目录写死为作者的 `/home/priyam22/...`；静态相机 TF 用位置参数给出 | 以后在独立工作区参数化日志目录；按模型测定安装外参，核查 Jazzy 接口 |
| `package.xml` | 已声明 rclpy、px4_msgs、tf2_ros、geometry_msgs；launch 中另有 image_proc、apriltag_ros 等运行需求 | 补查 launch、消息、NumPy、YAML 等依赖；不能把 colcon 成功当作运行依赖齐全 |
| README 的 `px4_gz_bridge` | 启动说明依赖另一个桥接包 | 查明来源、版本和实际功能；必要时在新工作区配置 ros_gz_bridge，包含图像、内参和时钟 |
| `offboard_experiment_manager.py` | 由该 ROS 节点发布 map→base_link；位置采用 `(x,-y,-z)`，姿态只用 heading | 不能说 PX4 自动发布了标准 ROS TF；该映射更接近 NED→NWU，工具注释也提到 NWU，但其他位置称 ENU；姿态还缺滚转/俯仰，必须统一约定并做轴向与姿态实验 |
| 同一管理器 | launch 声明 trajectory_type，代码路径直接调用 spiral_trajectory；状态切换后发布一次任务状态 | 核查参数是否实际生效、迟加入节点能否收到状态、控制权交接有无空档，不照搬 README 的半径说明 |
| `vision_guidance_controller.py` | 注释称 KF 位姿，但实际订阅 `/landing/tag_pose_map`，KF 订阅被注释 | 首先复现 raw 路线；KF 只做离线对照，注释不代替数据流证据 |
| 同一控制器 | ALIGN 后进入 DESCEND，按设定值递减高度；进入后没有持续用可见性和消息年龄阻止下降 | 本路线增加目标丢失、陈旧数据、横向偏差和高度基准检查；发出 land 不算已着陆 |
| README 与控制器 | README 称 open-loop，代码同时使用目标位姿与飞机位置做对准判断 | 分清任务轨迹、视觉外环、PX4 内环；不把它直接描述为经过验证的完整视觉闭环 |

原项目的恒位置 KF 分析是参考思路。平滑可能降低抖动，也可能增加滞后；收益取决于噪声、运动与参数。本项目没有数据前，不写“静态目标不需要 KF”这一普遍结论。

## 环境适配先做哪些判断

Ubuntu 24.04 对应 Jazzy，Gazebo 采用与 Jazzy 配套的 Harmonic。这个组合是选型依据，不等于用户现有 PX4 版本已经兼容。实际版本及安装来源记录在 [ENVIRONMENT](../ENVIRONMENT.md)。

1. 先只读记录系统、架构、PX4 commit、Gazebo、ROS、Python、编译器、QGC 版本及环境变量。Ubuntu 24.04 通常使用系统 Python 3.12，不把上游 Python 3.10 标识作为本机事实。
2. 建议另建 `~/vision_landing_ws`，只在单独终端加载 Jazzy 和这个工作区。不要混入 Humble 或旧 ROS overlay；不更改全局 shell 配置来“修好”一次实验。
3. PX4 与 `px4_msgs` 要按所选 PX4 版本核对消息定义；Agent 要与该版本 uXRCE-DDS client 兼容。把版本与来源写下来，不默认所有仓库的 main 可以混用。必要时查看该版本的 DDS 话题配置及官方消息版本兼容说明。
4. ros_gz 处理 Gazebo 图像、内参、时钟；Micro XRCE-DDS Agent 处理 PX4 与 ROS 2 的消息链路。它们不能互相替代。先发现实际话题，再写桥接映射，记录方向、类型和 QoS。
5. AprilTag 检测器的包来源、Jazzy 构建支持、组件插件名、参数和输出 frame 都要核验。标签族、ID、尺寸必须与模型一致；尺寸按所选检测器定义的边界测量，不能把含白边贴图宽度直接当标签尺寸。
6. 仿真模型、world 和配置放在独立工作区。优先验证 `GZ_SIM_RESOURCE_PATH` 等资源路径能否加载，保留原环境变量；不要照抄上游覆盖 PX4 `models/`、`worlds/` 的命令。资源可见不等于 PX4 已有对应 airframe 或 make target，缺少时先记录并单独设计适配。
7. 这次不动用户 Ubuntu 的 PX4、MAVSDK 和旧 ROS 源码。后续若必须换 PX4 版本，在独立副本中验证，先说明原因和差异，不能覆盖现有成果。

官方核对入口：[ROS 平台矩阵 REP-2000](https://github.com/ros-infrastructure/rep/blob/master/rep-2000.rst)、[Gazebo 与 ROS 配套](https://gazebosim.org/docs/harmonic/ros_installation/)、[PX4 ROS 2 指南](https://docs.px4.io/main/en/ros2/user_guide)、[Offboard 示例](https://docs.px4.io/main/en/ros2/offboard_control.html)。main 文档会变化，实验记录要附所用 PX4 版本的文档链接。

## 阶段一：先弄清系统和环境

### 第 01 课：画出一条完整的数据链

- **原理**：PX4 负责飞控内环和状态估计，Gazebo 提供动力学与传感器，ROS 2 负责感知与任务，QGC 用于观察和操作。MAVSDK/MAVLink 与 ROS 2/uXRCE-DDS 是不同接口。
- **实践**：读原项目 README 和上述审阅表，画出“图像→检测→TF→目标→设定值→PX4→飞机运动”以及状态反馈支路。标出桥接、Agent、QGC 各自连哪里；将旧成果与视觉待办分开。
- **验收**：不看图解释一次数据往返；指出画面能看到但 PX4 状态读不到时，应先查哪条链路。保存连接图和五个组件的职责说明。
- **变式/排错**：去掉 AprilTag 检测器，说明哪些功能仍可测试；避免把缺感知误判为飞控故障。

### 第 02 课：做一张真实版本表

- **原理**：操作系统、ROS、Gazebo、Python 和消息定义共同决定兼容性；软件名字相同不代表 ABI、插件或消息字段相同。
- **实践**：只读检查 `cat /etc/os-release`、`uname -m`、`printenv ROS_DISTRO`、`gz sim --version`、`python3 --version`；在确认过的 PX4 目录查看 Git 提交和本地改动。逐项说明命令读什么、预期输出是什么，再执行。记录包来源、代理与图形条件，未知项留空待查。
- **验收**：ENVIRONMENT 中每项都有实测值或“待核验”；写清 Jazzy/Harmonic 选型与现有安装的区别。保留输出，不用截图猜版本号。
- **变式/排错**：新终端中发现 ROS_DISTRO 不对时，追踪 source 链，先解决环境混用，不重装全部依赖。

### 第 03 课：恢复最小 SITL 基线

当前：单轮起降通过；以下重启、稳定性与日志要求仍待补齐。

- **原理**：先验证仿真、飞控和观察工具，才能把后续故障限定在视觉链路。模拟时间、墙钟时间和实时率不同。
- **实践**：按已核验版本启动普通 X500；QGC 查看模式、预检和状态，完成一次原地起降，记录启动顺序、日志位置和停止步骤。关闭后从新终端复现，观察至少 10 分钟的稳定性与实时率。
- **验收**：保存本次启动与重启记录，能找到 ULog；明确 commander/QGC 操作不是 ROS 自动控制，也不是旧实验的重复证明。
- **变式/排错**：复盘资源下载、代理或图形故障时，只改已定位的环节；不要同时引入自定义 world 和相机。

## 阶段二：让 ROS 2 先读懂、再控制 PX4

### 第 04 课：读状态，先不发控制命令

当前：命令行通信及 C++ `position_monitor` 的编译、运行、位置/速度接收通过；源码待同步、订阅路径待核对，30 秒记录和停源后的过期/断连验证尚未完成。控制话题存在已确认，ROS 2 Offboard 尚未完成。

- **原理**：uORB 经 uXRCE-DDS 暴露到 ROS 2；发现话题、收到数据、消息有效是三个不同条件。QoS 不兼容可能表现为有话题却没有样本。
- **实践**：核对 px4_msgs 与 Agent 后启动通信；使用 `ros2 topic list`、`ros2 topic info -v <实际话题>` 检查位置、状态和着陆消息。写一个最小只读节点，记录有效位、接收时间与更新频率，不发送解锁指令。
- **验收**：解释每个读到字段及单位；保存至少 30 秒状态记录。停掉数据源后，节点能显示“过期/断连”，不继续显示旧值为有效。
- **变式/排错**：区分消息类型不匹配、QoS 不匹配与 Agent 没连上；每次只改变一个条件。

### 第 05 课：坐标和高度算对再飞

- **原理**：PX4 局部位置通常是 NED，ROS 常用 ENU；机体系 FRD/FLU 与世界系不能混为一谈。标准位置换算为 ENU=(NED.y, NED.x, -NED.z)，FLU→FRD 则为 (x,-y,-z)，两者不同。世界原点有偏移时还要处理平移。
- **实践**：纸面计算北、东、上三个单位向量；用仿真小位移核对轴方向。区分 local z、相对起飞高度、标签平面高度和离地高度。姿态用旋转矩阵/四元数整体转换，不只给 yaw 改符号。
- **验收**：单位轴、往返变换、非零 yaw 三组检查通过；写出 3 m 上升在 NED 中对应的符号，说明原项目 (x,-y,-z) 为什么不能直接叫标准 ENU。
- **变式/排错**：把标签平面抬高 0.5 m，说明哪些高度阈值需要重算；先计算，尚不执行降落。

### 第 06 课：最小 Offboard 起飞、悬停、降落

- **原理**：OffboardControlMode 是存活信号，TrajectorySetpoint 是目标；发送切模式或解锁请求不等于执行成功。PX4 要求持续约 2 Hz 以上的存活信号，并在切换前预先发送，具体条件按所选版本核验。
- **实践**：用一个控制发布者，先持续发送有效保持目标和心跳，再检查状态与命令反馈，起飞至约 3 m、悬停、请求降落。教学初始发布频率选 20 Hz，记录实际频率、ACK、模式、位置和着陆状态；不运行 MAVSDK 控制程序。
- **验收**：同一配置完成 3 次原地流程；达到目标高度、稳定、着陆和解除武装都有反馈证据。另做一次心跳停止测试，记录实际 failsafe 行为与相关参数，不能只看是否摔落。
- **变式/排错**：命令被拒绝时不循环盲发，说明是未就绪、位置无效还是模式条件不足。只有本课通过才接视觉控制。

## 阶段三：把相机和标签放进场景

### 第 07 课：独立加载模型与静态标签

- **原理**：SDF 的 visual 决定外观，collision 决定接触；贴图尺寸、模型尺寸和检测器尺寸不是天然相等。模型资源路径与 PX4 启动配置是两件事。
- **实践**：在独立工作区准备下视相机模型、平地和固定标签，记录标签族、ID、黑色边界尺寸、位置与朝向。验证资源路径、父模型、材质和碰撞体；先只加载场景。
- **验收**：重启可找到资源；俯视截图能看清标签，尺寸和世界坐标可复核，模型没有悬空/穿地。不复制文件覆盖用户 PX4 源码树。
- **变式/排错**：模型出现而贴图缺失时分别检查 URI、路径和材质；缺少 PX4 airframe/target 时单列阻塞，不假称资源路径已解决全部适配。

### 第 08 课：桥接图像、内参和时钟

- **原理**：图像像素需要 CameraInfo 才能转换成视线；仿真节点若混用墙钟与模拟时钟，会出现 TF 外推和错误超时。
- **实践**：先列 Gazebo 实际传感器话题，再配置到 ROS 的 Image、CameraInfo 与 `/clock` 映射。查看分辨率、编码、K 矩阵、frame_id、stamp 和频率；对需要仿真时间的节点设置 use_sim_time。
- **验收**：图像与内参匹配，时间戳处于同一时间域；暂停/继续仿真时知道时间如何变化。保存桥接表和一小段消息证据。
- **变式/排错**：图像黑屏、只有图像没有内参、QoS 无数据分别定位；不要用“RViz 能打开”作为全部验收。

### 第 09 课：从针孔模型理解看见范围

- **原理**：近似关系 u=fx·X/Z+cx、v=fy·Y/Z+cy；这里 XYZ 属于 optical frame，Z 是沿光轴的深度。分辨率、视场、距离和标签像素边长共同影响检测。
- **实践**：固定相机姿态，记录几个已知距离下标签像素大小与成像位置；核对 camera optical 的 X 右、Y 下、Z 前方向。用实际内参估算标签覆盖范围。
- **验收**：给出至少三组距离/像素边长记录，解释远处难检出和近地标签出画面；不把 Z 深度直接等同于世界高度。
- **变式/排错**：相机倾斜后重新解释像素变化；区分视角问题与标签尺寸参数错误。

## 阶段四：检测正确，还要知道结果何时可信

### 第 10 课：先只识别标签

- **原理**：AprilTag 解码给出族和 ID，位姿估计还需要内参和真实边长；检测框正确不代表米制距离正确。
- **实践**：核对 Jazzy 中检测组件接口，接上整流图像和 CameraInfo，先看检测 ID 与角点。记录使用的包版本、参数、输入输出话题。
- **验收**：连续可见时识别到指定族/ID，遮住或移出画面后不再出现新检测；记录样本和原因，不把旧 TF 缓存当新检测。
- **变式/排错**：换成错误 ID 或族配置，确认节点如何表现；一次只改一个参数。

### 第 11 课：验证相机坐标系位姿

- **原理**：PnP 由平面角点、内参和实际尺寸估计位姿；尺寸设错会导致尺度误差，平面目标还有姿态歧义与噪声。
- **实践**：在几个已知位置和朝向比较估计位姿与场景真值。先将真值变换到同一相机系再比较，检查距离、轴符号、旋转和米/毫米单位。
- **验收**：至少三组位置和一个倾斜姿态的误差表；写清测量边界、时间与误差来源。临时门槛为距离误差不超过 10%，超出先排查；该值是教学门槛，尚未达成。
- **变式/排错**：人为把尺寸参数减半，预测距离估计变化再验证，复原配置后留一段解释。

### 第 12 课：给检测结果加“保质期”

- **原理**：可用目标至少满足正确 ID、有效数值、足够新、连续观测；Bool 可见标志不能独自证明位姿仍新鲜。
- **实践**：记录采样时间、接收时间、最后一次正确检测时间、丢帧和处理延迟。设计连续帧确认、过期拒绝和异常跳变检查；用录包或假消息做遮挡、冻结、错误 ID 测试。
- **验收**：暂以连续 5 帧确认、消息年龄 0.3 s 为待调参数；三个异常均使目标失效，理由有日志。按实测帧率重新检查门槛是否合理。
- **变式/排错**：暂停仿真与节点卡死不是同一种故障；区分仿真时间年龄与墙钟进程看门狗。

## 阶段五：从相机里的目标变成世界里的目标

### 第 13 课：量清相机安装外参

- **原理**：base_link→camera_link→optical 的刚体变换描述安装位置和方向；SDF 中的父子姿态要逐级组合，不能凭画面朝向猜三个欧拉角。
- **实践**：画出机体和相机三轴，逐级读取模型安装变换，建立静态 TF；核对 launch 中参数顺序，明确四元数顺序与角度单位。
- **验收**：三条单位轴经旋转后方向正确；有可复核的平移、旋转和模型来源。TF 不重复发布、不成环，frame 名字与图像一致。
- **变式/排错**：改变一项安装偏移，预测目标位置变化；看到镜像误差先查轴，不先调控制增益。

### 第 14 课：组合世界、机体和标签变换

- **原理**：T_map_tag = T_map_body · T_body_camera · T_camera_tag，矩阵方向必须一致。动态机体姿态需要完整 roll/pitch/yaw；只用 heading 会在倾斜时把相机测量转错。
- **实践**：从有效 PX4 位置和姿态建立经验证的世界/机体变换，在图像采样时间查询 TF，明确 map 原点与仿真世界原点偏移。处理查询失败、过期和仿真重置，禁止无条件用最新 TF 拼旧图像。
- **验收**：保存 TF 树、消息时间和数值演算；在多个飞机位置及倾斜姿态下，固定标签的 map 坐标仍应近似不变，并报告实际漂移。
- **变式/排错**：注入 100 ms 时间错位，解释运动时误差为何增大；真值只作验收，不替代感知输入。

### 第 15 课：不开视觉控制，先验收定位

- **原理**：固定物体的估计位置随飞机一起移动，通常说明变换、时序或原点有问题；控制增益无法修复这种错误。
- **实践**：使用已通过的基础飞行方式在几个安全位置悬停，记录 raw 目标位姿、机体姿态和场景真值。分别分析静止与移动段，形成偏差和抖动表。
- **验收**：建议初始门槛为静止目标水平 RMSE ≤0.10 m、无轴翻转和随飞机移动的系统漂移；至少三个观测位置。门槛不通过则回到第 11～14 课，不能继续下降。
- **变式/排错**：在不改变标签的位置下改变飞机 yaw，检查估计是否旋转漂移，并独立定位一处变换错误。

## 阶段六：先对准，再下降

### 第 16 课：定高对准

- **原理**：以世界系位置目标驱动 PX4 内环；横向误差 e_xy=p_tag−p_drone。位置目标更新、速度限制和到位判据不是同一个量。
- **实践**：保持约 3 m 高度，只更新水平目标；设置步长/速度边界。持续检查状态、感知新鲜度和误差，用同一发布者输出控制目标；目标丢失则保持已验证的安全目标并启动超时处理。
- **验收**：从至少三个不同水平偏移收敛；暂以误差 ≤0.15 m 且持续 2 s、水平速度足够小作为到位门槛，记录曲线与阈值。此课禁止进入下降。
- **变式/排错**：检查正负方向、超调和噪声导致的目标跳动；每次只调一个限制量，保存前后对照。

### 第 17 课：分段下降与暂停条件

- **原理**：对准一次不保证下降全程对准；相机视野随高度改变。高度应相对已确认的降落平面，设定高度到阈值不代表飞机真实到达。
- **实践**：按高度段减小目标高度，初始最大下降速度暂取 0.20 m/s。每段检查实测高度、水平误差、速度、目标年龄；偏差增大或目标失效立即暂停下降，超时走失败出口。
- **验收**：无遮挡下降与中途遮挡各一次；遮挡后日志证明高度目标停止递减，恢复后重新满足连续确认与对准条件才继续。保留目标高度和实际高度两条曲线。
- **变式/排错**：低空失去完整标签时，先分析可见范围；不能依赖无限期旧目标盲降。最终切 Land 的高度和允许条件必须通过仿真确认。

### 第 18 课：完成一次可核对的降落

- **原理**：Land 请求、飞控进入降落模式、触地、解除武装、停转是不同事件；不因程序进入 DONE 就宣布成功。
- **实践**：在受控平地环境串联对准、下降、切 Land，检查命令反馈与状态。以标签中心和实际接触后机体投影计算水平误差，注明机体参考点；归档 ULog 与任务日志。
- **验收**：一轮完整流程，有落地、解除武装和落点证据；如果声称电机停转，必须另有转速观测。单轮成功仅标“单轮通过”，不能标整阶段已稳定复现。
- **变式/排错**：模拟 Land 被拒绝或状态不更新，验证超时和退出；失败轮仍记录，不能删掉只留成功录像。

## 阶段七：把单轮动作变成任务

### 第 19 课：有边界地搜索

- **原理**：搜索间距要与相机覆盖范围和有效检测高度相配；螺旋并不自动保证覆盖，也不能无限扩大范围。
- **实践**：先用离散安全航点，再尝试螺旋；明确半径上限、速度、持续时间和场地边界。搜索只到预先定义的安全区域，确认正确目标连续可见后才交接。
- **验收**：测试目标在起点可见、偏离起点、完全不存在三种情况；不存在时在预算内结束，不无限绕圈。保存轨迹和终止原因。
- **变式/排错**：核对 trajectory_type 参数真的改变轨迹；解释搜索间距太大为什么会漏检。

### 第 20 课：状态机与控制权

- **原理**：状态机负责决定何时做事；每状态要有进入动作、持续动作、成功条件、超时和失败出口。两个节点同时发设定值会让行为难以解释。
- **实践**：整理 READY→TAKEOFF→SEARCH→ALIGN→DESCEND→LAND→COMPLETE，另设 HOLD/ABORT。选择单一控制发布出口，或实现可验证的交接；让新加入/重启节点能获取当前状态，不只依靠一次性事件。
- **验收**：写出状态转移表，使用假状态覆盖每个出口；搜索到视觉交接期间心跳连续、没有互相冲突的目标。解锁和模式条件由实际状态确认。
- **变式/排错**：视觉节点迟启动或重启，系统不能继续假定它已接管；日志必须说明控制权在哪。

### 第 21 课：失效测试

- **原理**：失去感知、失去 PX4 状态、失去控制链路需要不同处理。ROS 侧 HOLD 请求也可能因链路失效无法执行，必须核对 PX4 自身 failsafe。
- **实践**：在 SITL 逐项注入标签丢失、消息冻结、TF 失败、Agent 中断、控制节点退出和命令拒绝。先在地面或低风险基线验证，再做空中受控试验；记录故障时刻和飞控实际反应。
- **验收**：每类有触发、预期、实际、恢复步骤与日志；任何失效都不能继续正常下降。处理恢复时需重新确认状态，不自动沿旧任务位置继续。
- **变式/排错**：区分用户主动接管与通信中断；发生接管后停止争抢控制，不把接管完成当自主任务成功。

## 阶段八：用数据评价，自己复现

### 第 22 课：落点误差和重复实验

- **原理**：末端误差不是整条轨迹 RMSE；有偏差、抖动和失败率才能评价系统。地面真值与视觉估计必须独立，不能用自己估计的目标证明自己准确。
- **实践**：固定版本与参数，记录至少 10 轮尝试，覆盖三个初始偏移；保存失败轮。计算落地时 e=sqrt((x_land−x_tag)^2+(y_land−y_tag)^2)，明确时间点、参考系、单位和真值来源。
- **验收**：初始目标为成功率 ≥9/10、成功轮水平误差中位数 ≤0.20 m，报告最大值及每轮表格；另完成一次完整重启复现。这些是待验证的课程目标，未实测前不能写成成果。失败要分析，不为通过而事后改门槛。
- **变式/排错**：区分误差变小与只剩少数成功样本；报告包含异常轮数、手动干预和排除理由。

### 第 23 课：raw 与 KF 的离线对照

- **原理**：恒位置模型可以降低随机抖动，但可能产生滞后；Q/R 控制信任模型还是测量。静止且几乎不变的信号不适合直接用互相关估计可靠延迟。
- **实践**：对同一批带时间戳的 raw 数据离线滤波；使用相同时间范围和有效样本，比较真值误差、标准差、丢失恢复过程。固定参数后再对比，不让 KF 输出参与本轮飞行控制。
- **验收**：给出至少一组原始/滤波曲线、指标与参数，解释改善和退化。没有足够变化激励时，把延迟标为“不可可靠估计”，不硬报数字。
- **变式/排错**：改变 Q/R 观察响应；根据自己的数据决定是否值得后续闭环试验，不能沿用作者“raw 更好”的结论。

### 第 24 课：从空白终端独立复现

- **原理**：能重跑 launch 与能解释、修改和排错不同；交付应包含版本、启动顺序、输入、结果和失败边界。
- **实践**：按自己整理的说明从新终端启动，换一个安全标签位置复测，独立定位一个事先设置的配置错误。整理依赖锁定、配置、启动/停止步骤、日志索引和未解决问题；代码另行同步实际运行版本。
- **验收**：他人或隔几天后的自己能按 README 重现；能解释光轴、ENU/NED、目标新鲜度、Offboard 心跳与落地证据。只有实际源码、日志和复现记录齐全后才标完成。
- **变式/排错**：用十分钟回答“为什么看得见标签却不能降落”；列出当前限制，再决定是否研究移动平台，不能直接扩大验收范围。

## 状态与证据怎么记

每课分开记录：未开始 → 有指导实践 → 验收通过 → 独立复现。不要把“课表写完”“包编译过”“运行过一次”统称完成。每阶段三课均达到验收条件后才关闭阶段。

每天在 `daily/YYYY-MM-DD.md` 留下：课号、目标、实际环境、改动、命令及作用、关键输出、日志/图像路径、提示程度、失败原因、下一课入口。大体积 bag/视频不直接塞进 Git；记录可访问的存储位置、文件名和校验值，仓库保留小型摘要与分析配置。证据尚未取得时写“待归档”，不创建空报告冒充实验。

建议逐轮表头：run_id、版本/参数、初始位置、tag 位姿真值、开始/结束时间、结果、落点误差、是否人工干预、失败原因、ULog/bag/CSV 位置。只记录自己实际观察到的数据。

下一次接着第 04 课核对并同步已运行的 C++ 只读节点，补 30 秒记录和断连检测；同时补第 01～02 课的说明、版本 commit，以及第 03 课独立重启记录。先完成这些，再进入坐标和 Offboard，不直接执行上游整套 landing launch。
